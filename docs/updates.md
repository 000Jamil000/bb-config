# Обновления доработок: публикация и применение

Этот документ — обязательный порядок для агента, который применяет обновление
у пользователя, и для автора, который его готовит. Команды выполняются в
checkout этого репозитория на машине сервера BB.

## Что считается обновлением

- Сигнал для пользователей — **опубликованный стабильный GitHub Release** с тегом
  `vX.Y.Z`. Draft, prerelease, тег без релиза и обычные коммиты в `main`
  сигналом не являются: `main` — текущая разработка.
- Версии по SemVer: patch — совместимые исправления, minor — совместимые
  возможности, major — несовместимые изменения. Опубликованный тег не
  перемещается; исправление выходит следующей версией.
- Релиз закрепляется парой «тег + полный SHA коммита». Применяется только этот
  коммит. Если тег указывает на другой коммит, обновление останавливается.
- Каждый релиз несёт в своём коммите инструкцию `docs/releases/vX.Y.Z.md`
  (для человека и агента) и манифест шагов `docs/releases/vX.Y.Z.json`
  (для скрипта). Заготовки: `docs/releases/TEMPLATE.md`, `TEMPLATE.json`.
- Обновления самого BB и сторонних каталоговых плагинов идут своим путём
  (`bb plugin outdated`, `bb plugin update`). Релиз может только требовать их
  минимальную версию.

## Как пользователь узнаёт об обновлении

Плагин [Config Updates](../plugins/config-updates) проверяет релизы каждые шесть
часов и по запросу (`bb config-updates check` или «Проверить сейчас» в настройках
плагина). Он показывает версию, описание и кнопку **«Обновить с ИИ»**: в карточке над
нижним рядом боковой панели (значок загрузки) и в настройках плагина. Проверка
ничего не устанавливает. Ошибка сети или GitHub показывается как ошибка
проверки; отсутствие обновлений она не означает.

Кнопка (или `bb config-updates start`) создаёт тред агента в проекте этого
checkout и передаёт ему закреплённые тег и коммит. Пока такой тред существует
или открыт запуск в журнале, второй тред не создаётся.

Без плагина то же можно сделать вручную: взять тег и SHA со страницы релиза и
попросить агента выполнить этот документ.

## Порядок применения (для агента)

Скрипт `scripts/updates.py` печатает JSON. Коды выхода: 0 — успех, 1 — ошибка,
2 — остались шаги, 3 — нужно решение пользователя или подтверждение проверки.

1. **Получить релиз.** `python3 scripts/updates.py fetch vX.Y.Z --commit <sha>`.
   Команда забирает только этот тег, сверяет SHA и делает fast-forward. Локальные
   правки и расходящиеся коммиты она не трогает и завершается кодом 3: разберись
   с пользователем (commit, stash, слияние). `git reset --hard`, принудительный
   checkout и `git pull` из `main` запрещены.
2. **Прочитать инструкции** из закреплённого коммита: этот файл и
   `docs/releases/<версия>.md` каждого релиза между установленной версией и
   целевой. Пропущенные релизы применяются по порядку, их шаги не пропускаются.
3. **Открыть запуск.** `bb machine list --json` даёт машины;
   `python3 scripts/updates.py begin vX.Y.Z --commit <sha> --machines <id,id>`
   перечисляет все машины-исполнители, включая машину сервера, если на ней
   работают агенты. Ответ содержит план: незавершённые шаги и их описание.
   Код 3 означает, что обновление уже ведёт другой тред: не дублируй работу,
   открой тот тред. `--takeover` допустим, только если тот тред точно
   остановлен или удалён (`bb thread show <id>`).
4. **Выполнить шаги** в порядке плана.
   - Шаг на сервере: `python3 scripts/updates.py run vX.Y.Z/<шаг>`. Команда
     сначала проверяет фактическое состояние. Уже применённое только
     фиксируется (`how: existing`), миграция не повторяется. Иначе шаг
     применяется и проверяется снова (`how: applied`).
   - Шаг `where: executors` выполняется для каждой машины. На машине сервера:
     `run vX.Y.Z/<шаг> --machine <id>`. На другой машине выполни команды шага
     там штатными средствами BB (`bb terminal`, тред на той машине) и запиши
     результат: `record vX.Y.Z/<шаг> --machine <id> --status verified
     --evidence "<что проверено и что показало>"`.
   - Шаг без автоматической проверки (`kind: manual` без `verify`) выполняется
     по `.md` релиза и записывается через `record` с содержательным
     `--evidence`.
   - Плагин, которого у пользователя нет, не ставится: шаг получает
     `not-applicable`. Новый компонент (`introduces`) ставится только с согласия
     пользователя: `run … --install`; при отказе —
     `record … --status not-applicable --evidence "пользователь отказался"`.
   - Отключённый пользователем плагин обновляется, но остаётся отключённым.
   - Ошибку шага разбери: сопоставь окружение с инструкцией, исправь причину,
     повтори `run`. Не помечай шаг выполненным без проверки. Недоступная машина
     остаётся в остатке.
5. **Завершить.** `python3 scripts/updates.py finish`. Установленной считается
   старшая версия, все шаги которой и всех предыдущих проверены на сервере и на
   каждой указанной машине. При остатке код выхода 2: версия не повышается,
   остаток виден в `status`, кнопка обновления остаётся. Затем
   `bb config-updates check`.
6. **Сообщить пользователю** по компонентам и машинам: что уже было применено,
   что применено сейчас, что осталось и почему.

### Прерывание и повтор

Повтори шаги 1 и 3 с теми же тегом и SHA: `begin` того же владельца продолжает
запуск, план содержит только незавершённое. `run` безопасен для повторного
вызова. Машину, за которой остался долг, нельзя убрать из списка молча: она
возвращается в план, пока шаг не проверен или не записан как неприменимый.

### Что обновление не делает

- Не применяет снимок настроек автора: `scripts/restore.py` и `config/`
  предназначены для восстановления целой установки, а не для обновления.
- Не меняет личные настройки, аккаунты, маршруты, прокси, состав плагинов и
  выбранные компоненты сверх шагов релиза.
- Не делает commit и push в checkout пользователя.

## Журнал

`.local/updates/journal.json` — локальный, в Git не попадает, секретов не
содержит. Хранит установленную версию, открытый запуск (владелец — ID треда),
остаток прошлого запуска и записи «релиз/шаг, машина, статус, способ, время».
Ключ машины — `server` для шагов сервера и ID машины BB для исполнителей.
Наличие тега или свежего checkout установкой не считается: запись появляется
только после проверки. Потеря журнала безопасна: шаги будут проверены заново
по фактическому состоянию.

- `python3 scripts/updates.py status` — установленная версия, остаток, запуск.
- `python3 scripts/updates.py baseline vX.Y.Z --commit <sha> --note "…"` — для
  установки, сделанной сразу из релиза (например, восстановление целиком):
  шаги этой и более ранних версий больше не требуются. Не используй, чтобы
  скрыть невыполненные шаги.

## Для автора: разработка и публикация

Разработка и публикация разделены.

1. **Разработка.** Агент ставит порученное изменение в работающий BB автора,
   проверяет его и сохраняет в репозитории по `AGENTS.md`. Для изменения,
   которое должно дойти до пользователей, в той же задаче дополняются
   `docs/releases/vX.Y.Z.json` и `.md` будущей версии: шаг со стабильным ID,
   проверка фактического состояния, скрипт применения, повтор и откат.
   Повторяемые действия оформляются скриптами с режимами проверки и применения
   (например, `scripts/migrations/vX.Y.Z_<имя>.py --check|--apply`).
   Изменённый плагин получает новую версию в `package.json`: по ней шаг
   `local-plugin` отличает старую установку от новой.
   Проверка шага у автора: `python3 scripts/updates.py run vX.Y.Z/<шаг>
   --development`. Запись получает режим `development` и публикацией не
   считается.
2. **Commit и push** по поручению сохраняют разработку. Пользователи остаются на
   прежнем релизе.
3. **«Публикуй обновление»** — отдельное поручение. Агент на проверенном
   коммите выполняет:
   - `python3 scripts/updates.py validate vX.Y.Z`,
     `python3 -m unittest discover -s scripts -p 'test_*.py'`, тесты затронутых
     плагинов;
   - `python3 scripts/privacy_check.py --history`; в инструкциях и манифесте нет
     путей, ID машин, адресов и настроек автора;
   - сверяет diff от прошлого релиза с шагами: каждое изменение, требующее
     действия у пользователя, имеет шаг;
   - создаёт стабильный релиз на точном коммите:
     `gh release create vX.Y.Z --target <sha> --title "…" --notes-file <описание>`
     без `--draft` и `--prerelease`. Описание — раздел «Что изменилось» и ссылка
     на `docs/releases/vX.Y.Z.md` в этом теге.
4. **Установка автора после публикации.** Плагин покажет собственный релиз.
   «Обновить с ИИ» проходит тот же порядок: шаги, применённые при разработке,
   проверяются и получают запись `existing` без повторной миграции. Шаги для
   машин, где изменение ещё не стоит, применяются как у всех.

Проверки механизма: `python3 -m unittest scripts/test_updates.py` (из каталога
`scripts`: `python3 -m unittest test_updates`) и `npm test` в
`plugins/config-updates`.
